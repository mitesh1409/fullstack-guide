Notes  

This video, hosted by Mehul Mohan, explores a highly scalable and language-agnostic approach to API design used at his startup. Rather than relying on popular frameworks like GraphQL or tRPC, he advocates for a custom, modular structure that prioritizes control, simplicity, and AI-friendliness.

Below are the detailed notes from the video:

### 1. The Core Philosophy: "Framework Agnostic"

The instructor argues that while tools like ExpressJS, GraphQL, or tRPC are popular, they aren't strictly necessary for building a robust infrastructure [[01:11](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=71)].

* **The Goal:** Create a system that works for 5 APIs or 5,000 APIs equally well.
* **Key Advantage:** This approach gives you full control over the request lifecycle and makes it easier for AI agents to generate new endpoints without getting lost in "context rot" [[00:42](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=42)].

### 2. The Request Lifecycle

He breaks down the primary responsibilities of a backend when a request arrives [[01:48](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=108)]:

1. **Identify the Endpoint:** Determine which specific API is being called.
2. **Rate Limiting:** Protect the server from abuse.
3. **Input Validation:** Sanitize and check "untrusted" input.
4. **Run the Handler:** Execute the actual business logic.
5. **Return Response:** Send the processed data back to the client.

### 3. API Organization: Namespaces & Function Files

The startup uses a folder-based structure to organize APIs within a monorepo [[10:03](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=603)].

* **Namespaces:** APIs are grouped into namespaces (e.g., `public`). This allows for categorization and specific handling rules per group [[04:25](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=265)].
* **Two-File Pattern:** Each API endpoint consists of two main files [[10:22](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=622)]:
* **`constants.ts`**: Contains metadata, the **Input/Output schema** (using Zod for TypeScript), and **Rate Limit** settings (e.g., 60 requests per minute) [[11:39](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=699), [13:55](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=835)].
* **`run.ts`**: Contains the "meat" of the code—the actual handler that runs once validation is successful [[14:27](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=867)].
* *(Optional)* **`test.spec.ts`**: A third file for unit and integration testing [[11:04](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=664)].



### 4. Intentional Deviations from REST

The instructor highlights several "unpopular" but deliberate design choices his team made to simplify the system [[05:05](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=305)]:

* **POST for Everything:** Even "Get" requests use the `POST` method. This avoids issues with reverse proxies, caching, and the inability of `GET` requests to have a body [[05:44](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=344)].
* **Always Return 200 OK:** As long as the request reaches the backend infrastructure and is processed, the server returns a `200` status code [[06:04](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=364)].
* **Internal Error Handling:** Errors are handled within the JSON response body rather than via HTTP status codes.
* **Response Schema:** A standard JSON object with a `status` field (either `"okay"` or `"error"`) and an `error_message` string if applicable [[07:24](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=444)].



### 5. Validation and Security

* **Validation First:** Input validation is performed *before* authentication (Auth/DB calls) because it is computationally "cheaper" to check a schema than to query a database [[08:33](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=513)].
* **Zod for Type Safety:** They use the **Zod** library for runtime validation and to ensure type safety in their TypeScript environment [[12:17](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=737)].
* **Rate Limiting Layers:** Rate limits are applied first by IP address (for unauthorized users) and then by user account (for authorized users) [[14:11](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=851)].

### 6. Tools and Workflow

* **Requestly:** The instructor uses Requestly as a git-friendly API client to manage and debug endpoints. Because the API definitions are simple JSON files, they can be synced via Git across the developer team [[09:18](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=558)].
* **OpenAPI Specs:** By defining schemas in `constants.ts`, the system can automatically generate OpenAPI documentation for external users [[11:44](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=704)].

### 7. Scalability for AI Agents

A major benefit of this "Two-File" system is for **AI Agents**. An AI only needs to understand the context of the two template files to create a brand-new, fully functional API endpoint, making it highly efficient for automated development workflows [[15:27](https://www.youtube.com/watch?v=xRL9e1q8ndY&t=927)].
