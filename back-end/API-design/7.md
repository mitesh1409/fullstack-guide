HTTP Methods  

Once you've identified your resources, you need to decide how clients interact with them. HTTP provides a set of methods (verbs) that map naturally to common operations, and understanding when to use each one is crucial for interviews.

**GET** is for retrieving data without changing anything. Use GET for /events/{id} to fetch event details or /events to list all events.

**POST** creates new resources. When a user books tickets, you'd POST to /events/{id}/bookings with the booking details in the request body. The server assigns an ID and returns the newly created booking. POST is neither safe nor idempotent. In other words, calling it multiple times creates multiple bookings.

**PUT** replaces an entire resource with what you send, or creates it if it doesn't exist. If you're updating a user's profile completely, PUT to /users/{id} with the full user object. Unlike POST, PUT is idempotent, so sending the same data multiple times results in the same final state.

**PATCH** updates part of a resource. When a user changes just their email address, PATCH to /users/{id} with only the email field. Unlike PUT, PATCH is not guaranteed to be idempotent - the result depends on how you implement it. A PATCH that says "set email to X" is idempotent, but a PATCH that says "append to list" is not.

**DELETE** removes a resource. DELETE /bookings/{id} cancels a booking. It's idempotent because repeated calls leave the server in the same state (the resource stays deleted), even if the response codes differ (first call might return 204, subsequent calls might return 404).

The key here is idempotency, meaning whether repeated requests leave the server in the same state. GET, PUT, and DELETE are idempotent because calling them multiple times doesn't change the final result. POST and PATCH are not guaranteed to be idempotent, which matters when networks fail and clients retry requests. You don't want duplicate bookings from a retry.

Your approach is **spot on**. In fact, what you just described is the industry-standard way to solve this exact problem.

In microservices and API design, this unique identifier is commonly called an **Idempotency Key** (or Request ID). By introducing this key, you essentially turn a non-idempotent operation (`POST`) into an idempotent one at the application layer.

Here is a breakdown of how this is typically designed and handled in production systems like Stripe, AWS, or enterprise banking.

---

## How the Idempotency Key Workflow Works

Instead of putting the unique ID inside the request payload, it is highly recommended to pass it as a custom HTTP header (e.g., `Idempotency-Key: <UUID>`). This keeps your request body focused strictly on business data and allows your API gateway or middleware to intercept duplicate requests early.

### The Lifecycle of a Safe Retry

1. **Client Generates Key:** Step 1.
Before making the `POST` request, the client generates a unique identifier (typically a **UUID v4**).


2. **Server Checks Cache/DB:** Step 2.
The server receives the request and looks up the `Idempotency-Key` in a fast-access store (like Redis) or a dedicated database table.


3. **Branching Logic:** Step 3.
* **Scenario A (First time):** The key doesn't exist. The server processes the booking, saves the booking *and* the idempotency key, and returns a `201 Created`.
* **Scenario B (Retry/Duplicate):** The key *already* exists. The server skips the booking logic entirely and simply replies with the exact same response it generated the first time.


---

## Technical Edge Cases to Watch Out For

While the concept is straightforward, implementing it reliably requires handling a few tricky real-world scenarios:

### 1. In-Flight Requests (The Race Condition)

What happens if the client sends Request #1, it times out, and the client instantly sends Retry #2 *while Request #1 is still processing in the database*?

* **Solution:** When Request #1 starts, insert the key into Redis with a status of `STARTED` or `PROCESSING`. If Retry #2 arrives and sees `PROCESSING`, the server should return an HTTP `409 Conflict` or `423 Locked`, telling the client to wait and try again shortly.

### 2. Request Body Mismatch

What if a malicious actor or a buggy client sends a retry with an existing `Idempotency-Key`, but changes the payload (e.g., trying to book a completely different event or a different seat using the same key)?

* **Solution:** When saving the key on the server, save a cryptographic hash of the request body alongside it. When a retry comes in, verify that the incoming payload hash matches the original stored hash. If they don't match, return an HTTP `400 Bad Request`.

### 3. Key Expiration (TTL)

You don't need to keep these keys forever. Retries usually happen within seconds or minutes of a failure.

* **Solution:** Set a Time-To-Live (TTL) on your idempotency records. In Redis, a TTL of **24 to 48 hours** is usually more than enough for business operations like ticket bookings.

---

## Alternative Pattern: PUT for Updates/Upserts

While the idempotency key is ideal for `POST` (where the server generates the resource ID), ask yourself if the client could know the resource ID *ahead of time*.

If your system allows the client to generate the `booking_id` beforehand, you can switch the HTTP method from `POST` to `PUT`:

```http
PUT /events/{id}/bookings/{booking_id}

```

Because `PUT` is inherently idempotent, if a retry happens, the database will simply execute an `UPSERT` (Update or Insert). If the booking already exists, it just overwrites it with the exact same data, resulting in no duplicate records.

> **Recommendation:** If the server *must* control the lifecycle and creation of the ID, stick with **POST + Idempotency-Key header**. It is clean, decoupled from your business logic, and highly effective.
