## What is an API?

APIs enable two software components to communicate with each other using a set of definitions and protocols.  

Client <-----> Server <-----> Database

For example we have an application that lists all events and allows user to buy tickets for those events.  
Here Client will request for all events or specific event from Server,  
Server will then request Database to get required events data.  
Finally, Server will generate a response and return to the Client.

* REST
* GraphQL
* RPC
* Web Sockets
* SSE (Server Sent Events)
* Web RTC

---

In case of GraphQL, what are you going to do about N+1 query problem?  

You are just going to use a data loader.  
You are going to batch and make one query to get all of the venues based on the ids  
that were returned from the first query.

RPC vs REST

RPC is so much faster, then why don't we use it for client to server communication  
instead of REST?  

Because clients are incredibly diverse - web browsers, mobile apps, 3rd party developers etc. And they all need to understand your APIs without special setup.  
REST uses standard HTTP protocol that every client understands,  
it passes through firewalls easily, it provides human readable JSON  
that developers can easily debug and understand.  
RPC on the other hand, it requires that both sides agree on the specific protocol  
in the binary formats and so this is great if you can control both ends like  
internal microservices.  
For these reasons RPC is not a good choice when you deal with external clients.  

REST --> Kinda global language (like English) that everyone understands,  
         it can be used for both external as well as internal communication,  
         it is inefficient compared to RPC.  

RPC  --> Kinda internal language (like Spanish),  
         it can be used for internal microservice communication,  
         it is highly efficient compared to REST.
