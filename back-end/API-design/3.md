# Good APIs Vs Bad APIs: 7 Tips for API Design  
https://www.youtube.com/watch?v=_gQaygjm_hg  

---

This video by ByteByteGo outlines seven essential tips for designing robust, secure, and developer-friendly REST APIs. While the previous video focused on a custom, language-agnostic framework, this one leans more toward industry-standard RESTful conventions.

Here are the notes covering all the topics discussed in the video:

### 1. Use Clear and Logical Naming

Choose names that are straightforward and intuitive for developers [[00:23](https://www.youtube.com/watch?v=_gQaygjm_hg&t=23)].

* **Plural Naming:**  
Use plural nouns for resources (e.g., `/carts/123` instead of `/get_cart_123`). This clearly indicates that the user is interacting with a collection or a specific item within a group [[00:30](https://www.youtube.com/watch?v=_gQaygjm_hg&t=30)].

For example,  
/carts     -->  Collection of carts  
/products  -->  Collection of products  

* **Consistency:**  
Stick to a logical URL structure across all endpoints to make the API predictable.

### 2. Ensure Reliability through Idempotency

Idempotency means that making the same API call multiple times has the same effect as calling it once [[00:53](https://www.youtube.com/watch?v=_gQaygjm_hg&t=53)].

* **GET/PUT/DELETE:**  
These are typically idempotent by nature.  
Repeated `GET` requests return the same info.  
Repeated `DELETE` requests simply confirm the resource is gone [[01:23](https://www.youtube.com/watch?v=_gQaygjm_hg&t=83)].  
PUT requests update full resources, so repeated PUT requests have the same effect.  

* **POST/PATCH:**  
These are often **not** idempotent.  
Sending the same POST request twice might create duplicate resources. To fix this, we require a client-generated **Unique ID** to de-duplicate requests [[01:08](https://www.youtube.com/watch?v=_gQaygjm_hg&t=68)].  
PATCH request update part of the resource, so if we are updating a list/array using a PATCH request then the same request can lead to duplicate entries [[01:43](https://www.youtube.com/watch?v=_gQaygjm_hg&t=103)].  

### 3. Implement API Versioning

Versioning allows you to update your API without breaking existing applications [[01:51](https://www.youtube.com/watch?v=_gQaygjm_hg&t=111)].

* **URL Versioning:**  
Include the version in the path (e.g., `/v1/carts/123`). This lets you introduce a `/v2` while supporting backward compatibility for older clients [[01:59](https://www.youtube.com/watch?v=_gQaygjm_hg&t=119)].  

* **Communication:**  
Use well-documented release notes to help developers upgrade on their own timeline [[02:18](https://www.youtube.com/watch?v=_gQaygjm_hg&t=138)].  

### 4. Add Pagination

Pagination prevents overwhelming the consumer and the server with too much data at once [[02:26](https://www.youtube.com/watch?v=_gQaygjm_hg&t=146)].

Common pagination approaches are:  

* Page + Offset
* Cursor-based

* **Page + Offset:**  
Simple to implement (e.g., Page 2 = Records 11-20).  
However, it can be slow for large datasets because the database must count all rows from the beginning [[02:37](https://www.youtube.com/watch?v=_gQaygjm_hg&t=157)].

* **Cursor-based Pagination:**  
Uses a pointer (cursor) to fetch the next set of records.  
This is more accurate for high-frequency data changes and more performant for large datasets [[02:57](https://www.youtube.com/watch?v=_gQaygjm_hg&t=177)].

### 5. Use Query Strings for Sorting and Filtering

Query strings keep the API clean and flexible [[03:09](https://www.youtube.com/watch?v=_gQaygjm_hg&t=189)].

* **Clarity:**  
Parameters like `?sort_by=registered` or `?filter=color:blue` make it easy for developers to understand what data is being returned [[03:16](https://www.youtube.com/watch?v=_gQaygjm_hg&t=196)].

* **Extensible:**  
Additional filtering and sorting criteria are easy to add over time without breaking  
existing integration.

* **Cache Friendly:**  
Filtered results can be cached separately, improving performance for common searches [[03:32](https://www.youtube.com/watch?v=_gQaygjm_hg&t=212)].

### 6. Prioritize Security (Not an Afterthought)

* **Headers over URLs:**  
Never put sensitive credentials like API Keys in the URL.  
URLs are often logged in plain text by servers.  
Use **Authorization Headers** instead [[03:45](https://www.youtube.com/watch?v=_gQaygjm_hg&t=225)].

* **Encryption:**  
Enforce full **TLS encryption** (HTTPS) for all traffic to shield data in transit [[04:06](https://www.youtube.com/watch?v=_gQaygjm_hg&t=246)].  
Use HTTPS protocol.  

* **Access Control:**  
Verify tokens and keys on every single request before processing [[04:10](https://www.youtube.com/watch?v=_gQaygjm_hg&t=250)].  
Authenticate & Authorize important/sensitive API end-points.  

### 7. Keep Cross-Resource References Simple

When resources are connected, use clear paths rather than messy query strings [[04:20](https://www.youtube.com/watch?v=_gQaygjm_hg&t=260)].

* **Clean Paths:**  
Instead of a complex query to find an item in a cart like `/items?card_id=123&item_id=321`,  
use a direct path like `/carts/123/items/321` [[04:29](https://www.youtube.com/watch?v=_gQaygjm_hg&t=269)].

### 8. Plan for Rate Limiting

Protect your infrastructure from abuse or accidental overload by setting quotas based on IP address, user account, or endpoint category [[04:46](https://www.youtube.com/watch?v=_gQaygjm_hg&t=286)].

For example,  

* Free-tier customers are allowed to make 1000 requests per day  
* Any IP address is allowed to make 20 requests per min  
* Authorized users can make 100 requests per hour  
etc.
