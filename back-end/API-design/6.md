---

## Why they are missed (The Mechanics)

When you requested the first page, your cursor was established based on the last item you saw (ID 91).

When you ask for the next page, your application sends a query that essentially says:

*"Give me 10 events where the ID is **less than** 91, ordered by ID descending."*

```
Database State:
[110, 109, ... 101] -> Newly added (Invisible to your active scrolling)
[100, 99, ... 91]   -> Page 1 (Already viewed)
              ║
              ╚═══ Your Cursor (ID < 91)
              ║
[90, 89, ... 81]    -> Page 2 (What you fetch next)

```

Because the database filters for `ID < 91`, the new events (101 to 110) are mathematically excluded from your downward journey.

---

## How this is handled in real-world apps

Missing these items during a "scroll down" isn't actually considered a bug in cursor-based pagination—it’s often a **feature**. It prevents data duplication (the "pushed down" item glitch common in offset pagination).

However, because the user still needs to see new data eventually, systems use a few common strategies to bridge the gap:

### 1. The "New Activity" Banner (Twitter/X, LinkedIn style)

While the user is reading Page 1, a separate polling mechanism or WebSocket connection listens for new inserts. If new events drop in with an ID greater than the first item of Page 1 (`ID > 100`), the UI displays a toast message: *"10 new events available. Click to view."*

* **If clicked:** The UI resets, clears the current list, and fetches the absolute latest data starting from the top.

### 2. Forward Pagination (Polling/Pull-to-Refresh)

The application can periodically poll the backend specifically for new data by looking *above* the highest ID it has loaded:

```sql
SELECT * FROM events WHERE id > 100 ORDER BY id ASC LIMIT 10;

```

These are then prepended (added to the very top) of the user's feed without disrupting their current scroll position down below.

### 3. Infinite Scroll with Real-time Prepend

If it's a live dashboard, a WebSocket connection can push events 101–110 directly into the client's memory. The UI smoothly injects them at the top of the feed. The user's scroll position shifts down so their eyes don't lose their place, but the new items are now loaded.

---

> **Summary:** Cursor pagination ensures consistency moving forward (you will never see duplicate items on Page 2), but it essentially locks you into a snapshot of time for everything that happened *before* your cursor. To see what happened *after*, you have to look backward (upstream) using `id > 100`.
